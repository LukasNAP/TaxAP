# TX — findings

Status: **Layer 1 official source connected** (`server/tx-rates.mjs`, live-verified 2026-08-26 by actually running both `investigate-state.mjs TX` against production `XATXBD`/`ADDR`/`CUSMS` and `fetch-official-rates.mjs TX` against the Texas Comptroller's combined-city-rate table). **Address matching is needed for the general case — not NC-style.** The majority of TX's real ship-to volume (≈63%) sits on a generic single-city-name A+ code that structurally collapses two or more county-qualified official jurisdictions into one; today those splits happen to agree in rate for every high-volume city checked, so no live discrepancy is hiding in the bulk of the book, but one confirmed live stale rate was found on a smaller code (Midland), and a further handful of codes are genuinely ambiguous rather than clean matches. Not safe to build a naive name-join comparison without a human decision on how to handle the multi-county-split cities.

1,907 active TX ship-tos / 1,289 active TX customer assignments / 240 distinct tax-body codes seen (235 `TX*`-prefixed, 5 cross-context non-TX codes — see below). Cross-checked against the Comptroller's live "combined city and local sales/use tax" table (2,533 rows, `https://comptroller.texas.gov/taxes/sales/city.php`, fetched via the already-shipped `server/tx-rates.mjs` adapter) — the exact "published combined city/local totals" source named in this investigation's brief. The adapter also fetches the quarterly EDI control file (`taxrates.txt`) to validate the 6.25% state rate and effective quarter, but the file actually used for jurisdiction-level totals is the combined-city table, per the adapter's own `boundaryStatus` note: *"overlapping components are not summed; address-level tax responsibility remains a separate reconciliation step."* That caveat, written into the adapter before this investigation, turned out to describe a real and material gap, not a theoretical one — see below.

## Address matching

**Needed for the general case, for a structurally different reason than GA or SC.** Texas cities frequently straddle county lines, and the Comptroller's own combined-rate table publishes a **separate row per county-slice of the same city name** — e.g. `Dallas (Collin Co)`, `Dallas (Dallas Co)`, `Dallas (Denton Co)`, `Dallas (Kaufman Co)`, `Dallas (Rockwall Co)` all exist as distinct rows. A+ mostly stores just the bare city name (`TX0555` "Texas Dallas") with no county qualifier, so a specific ship-to's correct rate depends on which side of a county line its address actually sits on — the same "can't resolve from the code alone" shape as GA's ZIP-boundary problem, just driven by county lines instead of dense special-district overlap.

**Scale of the effect:** of the 235 real `TX*` codes (1,885 ship-tos after excluding cross-context and no-config rows):
- **100 codes / 485 ship-tos (25%)** have a description that maps to exactly one row in the official combined-city table — clean, unambiguous 1:1 comparison.
- **≈83 codes / ≈1,200 ship-tos (63%)** — including the state's six highest-volume codes (Dallas 255, Houston 149, Fort Worth 81, San Antonio 80, Austin 72, El Paso 68 ship-tos) — carry a bare city name that collides with 2+ county-qualified rows in the official table. For every high-volume city actually checked (Dallas, Houston not spot-checked directly but same shape confirmed for Fort Worth, Corpus Christi, Amarillo, Southlake), **all of the county-split rows currently carry the identical total (8.25%)** — so this ambiguity has zero live rate impact today for the biggest codes, but a single generic A+ code has no way to reflect a future divergence between those splits, an Ohio-transit-surcharge-shaped latent risk, not a current confirmed problem.
- **46 codes / 163 ship-tos (9%)** have no matching row anywhere in the official combined-city table under any name normalization tried — most look like unincorporated communities or informally-named areas (e.g. "Texas Spring," "Texas Longview Gregg," "Texas Pflugerville/Travis") that may not carry their own city-level local-option tax at all. Reported as **unavailable**, not guessed.
- **1 code (`TX000`), 2 ship-tos** has no XATXBD definition at all (`definitionStatus: "missing"`, not a labeled "DO NOT USE" row — see the Do-not-use section below).

**Real, live example of the multi-county-split risk actually mattering:** a smaller set of 12 codes / 64 ship-tos sit on city names where the official table's county-split rows genuinely **do** carry different totals (not just Dallas/Houston-style coincidental agreement) — `Garland` (bare 6.75% vs. `Garland (Collin Co)`/`Garland (Dallas Co)` both 8.25%), `Liberty Hill` (bare 6.75% vs. `(Williamson Co)` 8.25%), `Pearland`, `Schertz`, `Cedar Hill`, `Kilgore`, `Sweetwater`, `Cibolo`, `Terrell`/`Terrell Hills`. In every one of these except Midland, A+'s single rate happens to equal one of the real candidates — plausibly correct if the actual ship-tos are on that side of the county line, but **not confirmable without an address**, which this project does not fetch or expose. Texas's own official source also contains two flatly ambiguous duplicate-name rows — `Palestine` (6.75% and 8.25%, two rows, identical name) and `Sulphur Springs` (6.75% and 8.25%, same) — that can't be resolved by name matching at all, a data-quality wrinkle in the Comptroller's own table rather than an A+ problem.

**Scale check:** Texas has 254 counties and roughly 1,500 incorporated cities/towns; the Comptroller's combined-city table itself has 2,533 rows (reflecting the county-split duplication above, plus assistance-district variants like `Amarillo/Randall Co Assist Dist No. 1`). A+'s 235 real codes are ≈9% of that row count — the familiar "sparse, customer-driven coverage" shape already seen in MO/CO/NE/UT, not a full jurisdictional mapping, and not something a code-count comparison alone would have revealed as needing address matching.

## Rate comparability

**Partially confirmed, with one genuine live stale rate and several ambiguous-not-confirmed cases — do not treat as a clean pass.**

- **100 codes / 485 ship-tos** matched their single corresponding official row exactly — comparable and currently correct.
- **Confirmed live stale rate: `TX1421` "Texas Midland"** (9 active ship-tos) — A+ `currentRate` is **8.0%**, but the official table's only unambiguous candidate for the main city is **8.25%** (the Martin Co. portion, the only other real candidate, is lower still at 7.5%). A+'s value does not match *either* real jurisdiction, so this is a genuine stale rate independent of the address-matching question, not an artifact of the county-split ambiguity.
- **Ambiguous, not confirmed: `TX0792` "Texas Garland" (20 ship-tos)** and **`TX1217` "Texas Liberty Hill" (1 ship-to)** — A+'s rate (8.25% for both) matches the county-qualified official row but not the bare-name row (6.75% for both). Whether this is correct depends on which side of the county line those specific ship-tos are actually on — cannot be resolved without address-level matching, and must not be reported as a confirmed stale rate.
- **Ambiguous, official-source-internal: `TX1663` "Texas Palestine" (3 ship-tos)** and **`TX2167` "Texas Sulphur Springs" (2 ship-tos)** — the Comptroller's own table has two rows sharing the identical place name at different totals (6.75% / 8.25%), with no distinguishing county or code visible in the fetched snapshot. Genuinely unresolvable from this data; needs a human decision or a more granular Comptroller data pull, not a guess.
- No hidden surcharge/layering question analogous to Ohio's transit tax was found — Texas's local rate is a single capped (2%) combined figure per jurisdiction in the Comptroller's own published table, so (unlike OH/NY/MN) there is no separate "is this already netted in" question once a jurisdiction is correctly identified. The open question here is entirely about *which* jurisdiction a given code represents, not what's baked into the number once it's picked.

## Do-not-use and cross-context findings

**`TX000` — not a labeled placeholder, a missing definition.** 2 of 1,907 active ship-tos (0.1%) reference tax-body `TX000`, which has **no `XATXBD` row at all** (`definitionStatus: "missing"`, `description: null`) — structurally different from the AL000/MN000/ND000/NE000/UT000/WA000 pattern (those are real, configured rows explicitly tagged "DO NOT USE"). At 0.1% this is nowhere near the blocking double-digit shares seen in AL/MN/NE/UT/WA. **Open question, not resolved here:** `readStateDetail`'s automatic retired-tax-body exclusion could in principle be hiding a genuine "DO NOT USE"-tagged `TX0xx` code with real ship-tos the same way other states' placeholders were found — this investigation's reconciliation (sum of all 240 returned tax bodies' ship-to counts = 1,907 = the header's `activeShipTos` exactly) shows no *gap* between the two, which is evidence against a large hidden placeholder, but does not prove one doesn't exist at a small scale, since the header total itself is computed after any such exclusion.

**22 of 1,907 active TX ship-tos (1.2%) carry a non-Texas tax body** — the same `SASTXB` cross-context pattern already documented for GA/NV/others:
- `MX000` "Mexico no tax" — 17 ship-tos
- `ZTEMP` "TAX BODY TEMP USE" — 2 ship-tos (itself a DO-NOT-USE-shaped generic placeholder, not TX-specific)
- `DR000` "DOMINICAN REPUBLIC" — 1 ship-to
- `SC068` "SC 02130 Charleston" — 1 ship-to
- `VA043` "Virginia Henrico" — 1 ship-to

All five should be excluded from TX-specific findings with a visible count, the same way GA's live run excludes its NC060/NC041/SC126/CA1163/PA000 outliers. None of these are TX-prefixed codes mistakenly naming another state — every one of the 235 real `TX*`-prefixed codes' descriptions was eyeballed and each one actually says "Texas"/"TEXAS," so no SC3622-style ("South Dakota Vermillion") wrong-state contamination was found *inside* the TX-prefixed set itself.

## Open questions / do instead if building

- **Before building:** decide how to handle the ~63% of ship-to volume sitting on a bare-city-name code that collides with multiple county-qualified official rows. Two honest options: (a) ship a flat name-join comparison now, since every high-volume city checked currently agrees across its splits, while flagging in the UI that this is a known simplification that would silently miss a future divergence (the NV-TID/OH-transit playbook); or (b) build real address/county-level matching before comparing these codes at all. Do not silently pick one candidate rate to compare against without disclosing the ambiguity.
- **Before building:** get a human decision on the confirmed `TX1421` Midland stale rate (A+ 8.0% vs. official 8.25%/7.5%, matches neither) — this is real regardless of the address-matching question.
- **Before building:** get a human decision on `TX0792` Garland and `TX1217` Liberty Hill — likely correct (matches the county-qualified candidate) but not confirmable without an address; do not report these as confirmed stale rates.
- **Before building:** decide how to handle `TX1663` Palestine and `TX2167` Sulphur Springs — the official Comptroller table itself carries two rows with the identical name and different rates; may need a follow-up pull of the Comptroller's raw EDI detail file (with place/county FIPS codes) rather than the combined-city HTML table to disambiguate, or may simply need to be flagged "ambiguous" indefinitely.
- **Before building:** decide how to handle the 46 codes / 163 ship-tos with no matching official row at all — confirm whether these are genuinely unincorporated areas with no city-level local tax (in which case the correct comparison is state + county only, a different official source than the combined-city table used here) before reporting them as gaps.
- Exclude the 22 cross-context ship-tos (`MX000`, `ZTEMP`, `DR000`, `SC068`, `VA043`) from any TX-specific comparison, with a visible count, same as GA's pattern.
- Use `SASTXB` (ship-to level), not `CMTXBD` (customer level), for the same reason already established for NC/GA/NV.
- If real address-level matching is ever built for TX, the Comptroller's raw quarterly EDI file (`taxrates.txt`, already fetched by `server/tx-rates.mjs` but only used today for state-rate/quarter validation) carries place/county/special/transit FIPS-style codes per row and could be the real starting point — closer to GA's boundary-file shape than the combined-city HTML table used for this investigation's rate comparison.
